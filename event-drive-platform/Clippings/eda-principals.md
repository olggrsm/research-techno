Цель документа сформировать ADR для построения платформы на архатиктуре EDA хореогрфии.
Принципы реализации EDA:
1. Стэк возможных реализаций шины событий 

1. Kafka — сбалансированный лидер

Выбирайте Kafka, если нужны одновременно высокая пропускная способность, долговременное хранение событий, replay, несколько независимых подписчиков и зрелая безопасность.

Используйте TLS + mTLS для транспорта и взаимной аутентификации; для сервисных учетных записей — SASL/SCRAM-SHA-512 или OAuth/OIDC, а авторизацию — через ACL.

Для живучести развертывайте минимум 3 брокера с replication factor не ниже 3 и min.insync.replicas=2.

Для горизонтальной изоляции выделяйте отдельные топики под bounded contexts, отдельные consumer groups для независимых процессов и ACL по принципу минимальных прав.

Обязательно закладывайте idempotent consumers, correlation ID, DLQ и schema/versioning: брокер обычно дает at-least-once, поэтому повторная доставка — норма.

Когда выбирать: высоконагруженные доменные события, audit log, event sourcing, аналитика, интеграция многих команд и систем.

2. NATS JetStream — лучший по latency и простоте

Выбирайте NATS JetStream, если критичны низкая задержка, компактный облачно-нативный кластер и гибкая изоляция между командами/доменами.

mTLS требует сертификат от каждого клиента и отклоняет цепочки, не доверенные сервером; JWT и NKeys позволяют строить четкую модель идентичности и прав.

Permissions на уровне account/subject дают хорошую изоляцию: сервис видит только разрешенные subject-пространства.

JetStream подходит для durable consumers, replay и распределенной обработки, но для очень долгого хранения и тяжелой аналитики Kafka обычно практичнее.

Когда выбирать: микросервисы с событийными интеграциями, телеметрия, real-time сценарии, платформенная шина с жесткими требованиями к изоляции.

3. Архитектурный шаблон
   Оптимальная хореография обычно выглядит так:

text
Domain Service A
-> Transactional Outbox
-> Event Broker (Kafka / NATS JetStream)
-> Service B (consumer group 1)
-> Service C (consumer group 2)
-> Analytics / Audit (consumer group 3)
Каждый сервис публикует факт, а не команду: например, OrderPlaced, а не SendEmail.

Подписчики обрабатывают события независимо, масштабируются отдельно и не знают друг о друге.

Сбой или замедление одного потребителя не блокирует продюсера и других подписчиков — это ключевое преимущество broker-based хореографии.

Для бизнес-процессов с компенсациями используйте Saga: хореография подходит для слабосвязанных реакций, но сложные длинные процессы с явным исходом и rollback иногда требуют локальной оркестрации или durable workflow.

Практическая рекомендация
Для большинства enterprise-сценариев выбирайте:

Apache Kafka — если приоритетны безопасность, масштаб, retention, replay и зрелая экосистема.

NATS JetStream — если приоритетны latency, простота, сильная multi-tenant изоляция и lightweight-инфраструктура.

RabbitMQ — если это прежде всего система задач и маршрутизации, а не потоковая платформа событий.

Не выбирайте брокер только по «скорости»: важнее требуемый порядок событий, horizon replay, retry-семантика, retention, стоимость эксплуатации, модель безопасности и способность изолировать домены.

5. Идемпотентность потребителя.
Идемпотентность потребителя означает, что повторная обработка одного и того же события не меняет итоговое состояние системы и не порождает дублирующих побочных эффектов. В EDA это обязательно, поскольку брокеры обычно гарантируют at-least-once доставку, а не строго однократную.

Базовый механизм
Используйте стабильный ключ идемпотентности и персистентный реестр обработанных операций.
Производитель присваивает событию уникальный event_id (UUIDv7/ULID) и включает его в envelope события.

Потребитель извлекает ключ и атомарно проверяет, не была ли уже выполнена соответствующая бизнес-операция.

Если ключ уже зафиксирован — событие признается дубликатом: подтверждается и пропускается.

Если нет — потребитель выполняет бизнес-логику и в той же транзакции сохраняет ключ как обработанный.

Ключ должен обозначать конкретную логическую операцию, а не просто correlation ID: один correlation ID может относиться к нескольким независимым событиям.

Надежная схема в БД
Самый надежный вариант — совместить dedup-таблицу с идемпотентной записью бизнес-данных.

sql
CREATE TABLE processed_events (
consumer_name  VARCHAR NOT NULL,
event_id       VARCHAR NOT NULL,
processed_at   TIMESTAMPTZ NOT NULL,
result_hash    VARCHAR,
PRIMARY KEY (consumer_name, event_id)
);
Обработка:

sql
BEGIN;

INSERT INTO processed_events (consumer_name, event_id, processed_at)
VALUES (:consumer, :event_id, now())
ON CONFLICT DO NOTHING;

-- если affected_rows = 0: duplicate, commit и ack
-- если affected_rows = 1: выполнить бизнес-изменения

UPDATE orders
SET status = 'PAID'
WHERE order_id = :order_id
AND status <> 'PAID';

COMMIT;
Важно: проверка и фиксация ключа должны быть атомарными. Обычная последовательность «SELECT → обработать → INSERT» уязвима к гонке при параллельных консьюмерах; применяйте INSERT ... ON CONFLICT DO NOTHING, SET IF NOT EXISTS или уникальный constraint.

Идемпотентные операции
Предпочитайте проектировать саму операцию идемпотентной, а не полагаться только на dedup-таблицу.

Операция	Неидемпотентно	Идемпотентно
Создание заказа	INSERT INTO orders ...	INSERT ... ON CONFLICT (external_order_id) DO NOTHING
Списание средств	UPDATE balance = balance - 100	Создать ledger-запись с уникальным payment_intent_id; баланс — производная величина
Отправка письма	Отправить письмо	Проверить notification_id в БД, затем отправить и сохранить статус
Резервирование товара	UPDATE stock = stock - 1	Создать reservation с уникальным reservation_id, затем уменьшить доступный остаток
Для финансовых и инвентарных операций особенно хорош ledger/event-sourcing: повторное применение события либо не меняет агрегат, либо детерминированно дает тот же результат.

Обработка внешних вызовов
Повторная доставка особенно опасна, когда потребитель вызывает внешнюю систему: платежный шлюз, SMS-провайдер, почтовый сервис.

Перед вызовом сохраните IN_PROGRESS с уникальным idempotency_key.

Передавайте этот ключ во внешний API, если он поддерживает идемпотентность.

После успешного ответа сохраните результат и статус COMPLETED.

При сбое между внешним вызовом и сохранением результата используйте запрос статуса по ключу, а не слепой повторный вызов.

Пример: при оплате не отправляйте повторно charge с новым идентификатором. Отправляйте тот же idempotency_key, чтобы провайдер вернул результат исходной операции.

Kafka и порядок событий
В Kafka идемпотентность потребителя решает дубли, но не отменяет необходимость обработки внеочередных событий.

Используйте event_id для дедупликации.

Используйте event_time, sequence или номер версии агрегата для отбрасывания устаревших событий.

Храните последнюю примененную версию/offset на уровне агрегата: событие применяется только если его версия больше уже примененной.

Не рассчитывайте на строгий глобальный порядок между разными топиками и партициями.

Для критичных потоков можно использовать транзакции Kafka и идемпотентного продюсера, но это не заменяет идемпотентность бизнес-логики потребителя: сбой после commit, повторная доставка или обработка другим сервисом все равно требуют защиты на стороне подписчика.

TTL и очистка
Храните processed_events ограниченно, но не удаляйте записи слишком рано:

TTL должен превышать максимальный retention брокера и максимальное время retry/redelivery.

Для платежей, изменений прав доступа и финансовых операций лучше хранить дедуп-записи долго или бессрочно.

Для некритичных уведомлений обычно достаточно нескольких дней или недель.

Индексируйте таблицу по (consumer_name, event_id); это позволяет разным потребителям независимо обрабатывать одно событие без взаимной блокировки.

Что тестировать
Идемпотентность нельзя считать свойством «по умолчанию» — ее нужно проверять явно.

Повторная доставка одного события: результат состояния не меняется.

Параллельная доставка двух копий: создается только один побочный эффект.

Сбой после бизнес-операции, но до ack: повтор не дублирует операцию.

События в неправильном порядке: устаревшее событие не перезаписывает более новое состояние.

Восстановление потребителя после сбоя: обработка продолжается без дублей и потерь.

Практическое правило
Минимальный production-набор: event_id в контракте события + атомарная dedup-запись + идемпотентная запись в доменной БД + идемпотентные внешние вызовы + DLQ и наблюдаемость. Это закрывает основные риски at-least-once доставки, гонок и частичных сбоев.

5.Способ обработки событий
События вне порядка нужно обрабатывать не попыткой «навсегда упорядочить поток», а явной доменной политикой: применять только более новые изменения, буферизовать в допустимом окне либо ждать обязательные события. В распределенной EDA полный глобальный порядок обычно недостижим и не нужен.

Сначала определите порядок
Выберите, какой порядок важен для конкретного агрегата или бизнес-процесса:

Порядок по сущности: события одного order_id, user_id, account_id должны применяться последовательно.

Порядок по версии: событие с версией 5 не должно быть перезаписано поздно пришедшей версией 3.

Порядок по времени события: важно для аналитики, окон и расчетов, но не всегда для изменения состояния.

Порядок причинно-следственный: например, OrderCreated обязан предшествовать OrderPaid; его лучше обеспечить на уровне producer/partition, а не надеяться на брокер.

В событие включайте как минимум:

json
{
"event_id": "01J...",
"aggregate_id": "order-9182",
"event_type": "OrderPaid",
"event_version": 7,
"occurred_at": "2026-11-15T09:30:00Z",
"correlation_id": "..."
}
Стратегия версий
Для изменения состояния чаще всего лучший подход — last-writer-wins по доменной версии, а не по времени обработки.

sql
UPDATE orders
SET status = :new_status,
version = :event_version
WHERE order_id = :aggregate_id
AND version < :event_version;
Если affected_rows = 0, событие устарело: его можно ack-нуть, залогировать и не применять. Это защищает от ситуации, когда поздний OrderCancelled приходит после уже примененного OrderShipped.

Для событий с нечисловой версией используйте occurred_at или монотонный sequence, но учитывайте рассинхронизацию часов; event_version от источника обычно надежнее.

Буферизация и watermark
Если бизнесу нужен строгий порядок в небольшом окне, буферизуйте события по ключу агрегата и обрабатывайте их в порядке event_version или occurred_at.

text
Вход: v5, v3, v4
Буфер: v3, v4, v5
Обработка: v3 -> v4 -> v5
Ограничьте буфер tolerance window — например, 30 секунд, 5 минут или N событий. По истечении окна применяйте политику для «поздних» событий: обработать с компенсацией, отправить в DLQ, отбросить или выдать предупреждение. Такой компромисс между задержкой и корректностью является стандартным для потоковой обработки.

Watermark помогает понять, до какого момента времени система считает поток «закрытым» и может безопасно завершить окна или перейти к следующему состоянию. События, поступившие после watermark, считаются поздними и обрабатываются по отдельной политике.

Ожидание обязательных событий
Если OrderPaid невозможен без OrderCreated, не применяйте его немедленно: сохраните как pending и активируйте, когда появится недостающее событие.

text
Получено: OrderPaid(v2)
OrderCreated отсутствует
-> сохранить pending
-> при получении OrderCreated(v1) применить v1, затем v2
Это уместно для коротких и критичных цепочек, но создает состояние ожидания, таймауты и необходимость компенсаций. Для сложных длительных процессов может быть лучше использовать saga либо локальную оркестрацию, а не пытаться восстановить порядок исключительно на потребителе.

Компенсация вместо переупорядочивания
Для необратимых действий — платеж, отправка уведомления, списание товара — иногда правильнее не ждать, а обработать событие и затем компенсировать позднее поступившее более старое.

Пример:

Пришел OrderCancelled(v5) — заказ отменяется.

Затем пришел OrderPaid(v3).

Потребитель видит, что v3 < v5, и не меняет состояние на PAID.

Если платеж уже был инициирован ранее, запускается компенсация: refund, отмена резервирования или ручная эскалация.

Такой подход лучше, чем бесконечное буферизирование, когда нельзя заранее знать, сколько событий задержится.

Практические правила
Не используйте время получения как основу бизнес-порядка: оно отражает доставку, а не факт в предметной области.

Партиционируйте по aggregate_id, если требуется порядок внутри сущности; в Kafka это сохраняет порядок внутри партиции, но не между партициями.

Идемпотентность обязательна: одно и то же событие может быть доставлено повторно, поэтому повтор не должен менять состояние.

Разделяйте факт и реакцию: OrderPaid — факт; отправка письма, начисление бонусов и резервирование — отдельные идемпотентные подписчики.

Логируйте отклоненные события с причиной: stale_version, missing_dependency, late_beyond_tolerance, duplicate.

Мониторьте метрики: доля out-of-order событий, максимальная задержка, размер буфера, число событий в DLQ и количество компенсаций.

Выбор политики
Ситуация	Рекомендуемая политика
Изменение статуса заказа, профиля, счета	Версионность / conditional update
Нужен строгий порядок в пределах секунд или минут	Буфер + watermark + tolerance window
Есть обязательные предшественники	Pending state + ожидание + timeout
Действие необратимо и уже выполнено	Компенсирующее действие или DLQ
Аналитика и агрегаты	Event time, окна, watermark, late-event policy
Платежи и деньги	Идемпотентность + ledger + компенсации
Для большинства микросервисных сценариев начинайте с версионного conditional update + идемпотентности. Буферизацию добавляйте только там, где бизнес явно требует строгой последовательности и может tolerate дополнительную задержку.

6. Реализовать версионность сущностей в БД
   Версионность сущности в БД — это монотонный номер состояния, который позволяет безопасно применять изменения: обновление принимается только если версия не изменилась с момента чтения. Для EDA это основной способ отсекать дубликаты и события, пришедшие вне порядка.

Базовая схема
Добавьте в таблицу сущности колонку version и увеличивайте ее при каждом успешном изменении:

sql
CREATE TABLE orders (
order_id     UUID PRIMARY KEY,
status       VARCHAR NOT NULL,
total_amount NUMERIC NOT NULL,
version      BIGINT NOT NULL DEFAULT 0,
updated_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
Чтение:

sql
SELECT status, version
FROM orders
WHERE order_id = :order_id;
Условное обновление:

sql
UPDATE orders
SET status = :new_status,
version = version + 1,
updated_at = now()
WHERE order_id = :order_id
AND version = :expected_version;
Если affected_rows = 1, изменение принято. Если 0, кто-то уже изменил сущность: это конфликт конкурентного доступа или устаревшее событие. Такой compare-and-swap-подход называется optimistic concurrency control: он не держит блокировку строки на весь период бизнес-операции.

Обработка конфликта
Не игнорируйте нулевое число затронутых строк — это сигнал пересчитать решение на актуальном состоянии.

text
1. Прочитать order: version = 7
2. Принять решение: approve(order)
3. UPDATE ... WHERE version = 7
4. affected_rows = 0
5. Повторно прочитать актуальную версию
6. Повторно применить бизнес-правила
7. Обновить с новой expected_version
   Повтор следует ограничить: например, 3–5 попыток с коротким backoff. Если конфликт повторяется, отправьте команду в очередь на повторную обработку или верните пользователю понятную ошибку «данные изменились, обновите и повторите».

Версионность в EDA
Для событий храните не только текущую версию сущности, но и версию события-источника:

json
{
"event_id": "01J...",
"aggregate_id": "order-9182",
"event_type": "OrderPaid",
"event_version": 7,
"occurred_at": "2026-11-15T09:30:00Z"
}
Потребитель применяет событие только если его версия строго больше текущей версии агрегата:

sql
UPDATE orders
SET status = :event_status,
version = :event_version
WHERE order_id = :aggregate_id
AND version < :event_version;
Ситуация	affected_rows	Действие
Событие новое	1	Применить, ack
Дубликат или устаревшее событие	0	Ack, залогировать как stale_or_duplicate
Событие с меньшей версией приходит после большего	0	Не откатывать состояние; при необходимости компенсировать
Это защищает от повторной доставки и out-of-order событий, но не заменяет идемпотентность: для побочных эффектов — платежей, писем, резервирований — нужны отдельные идемпотентные ключи и ledger-записи.

Версионность событий
Если состояние сущности строится из событий, используйте версию не только в проекции, но и в event store. Каждое событие получает номер в потоке агрегата, а запись нового события требует ожидаемой версии.

sql
CREATE TABLE order_events (
aggregate_id UUID NOT NULL,
event_version BIGINT NOT NULL,
event_type VARCHAR NOT NULL,
payload JSONB NOT NULL,
occurred_at TIMESTAMPTZ NOT NULL,
PRIMARY KEY (aggregate_id, event_version)
);
При добавлении события:

sql
INSERT INTO order_events (
aggregate_id, event_version, event_type, payload, occurred_at
)
VALUES (
:aggregate_id, :expected_version + 1, :event_type, :payload, now()
);
Уникальный ключ (aggregate_id, event_version) гарантирует, что два конкурентных писателя не смогут одновременно добавить одну и ту же версию: второй получит constraint violation и должен перечитать агрегат и повторить команду.

Альтернативы версии
Механизм	Когда подходит	Ограничения
version BIGINT	Большинство доменных сущностей	Нужна явная логика retry/conflict
updated_at	Простые CRUD-сущности	Часы БД и точность времени могут быть ненадежны
Content hash	Защита от произвольных изменений полей	Сложнее отлаживать и поддерживать
Event stream version	Event sourcing, аудит, replay	Требует event store и проекций
Database row lock	Короткие критичные транзакции	Плохо масштабируется при долгих операциях
updated_at можно использовать как оптимистичную версию, но монотонный version обычно предпочтительнее: он не зависит от часов, прост в отладке и однозначно показывает последовательность изменений.

Важные правила
Инкрементируйте version только при успешной мутации; чтение версию не меняет.

Включайте version в API-ответы, если клиент редактирует сущность: он передает ее обратно как expected_version.

Не используйте версию как глобальный счетчик: она должна быть уникальна в пределах одной сущности или aggregate stream.

Для событий применяйте version < event_version, а не version = expected_version, если допустима доставка событий в произвольном порядке.

Логируйте отклоненные события с кодом причины: stale_version, duplicate_event, missing_dependency.

Для финансовых сущностей сочетайте версионность с ledger: баланс должен быть производным от неизменяемых транзакций, а не единственным хранимым значением.

Практический шаблон
Для сервиса, обрабатывающего события заказа:

sql
BEGIN;

UPDATE orders
SET status = :new_status,
version = :event_version,
updated_at = now()
WHERE order_id = :order_id
AND version < :event_version;

-- affected_rows = 0 -> commit, ack, log stale/duplicate
-- affected_rows = 1 -> выполнить зависимые операции, commit, ack

COMMIT;
Если в одной транзакции есть и изменение заказа, и запись в processed_events, это дает одновременно версионность, идемпотентность и атомарность обработки. Для конкурентных writers ключевая гарантия должна опираться на constraint или conditional update в БД, а не только на проверку версии в коде приложения.
