# Сага против durable workflow: сравнительный анализ для решения X-4

Статус: исследование, не решение. Дата: 2026-11-15. Основание для `docs/adr/domain/0009` (пока не написан).

Вопрос из требований (X-4): «Долгие процессы ДОЛЖНЫ выполняться как saga или durable workflow с идемпотентными компенсациями». Требование допускает оба варианта и не выбирает между ними. Этот документ сводит варианты и выводит из них кандидаты в требования, чтобы ADR выбирал из проверенных фактов, а не из общих соображений.

Метки достоверности — как в `docs/eda-platform-requirements.md`: [О] сверено с первоисточником, [В] заявление вендора, [Н] независимый источник по выдержке, [?] не подтверждено.

## 1. Что именно решает X-4

Три разных вопроса обычно смешиваются под словом «сага»:

1. **Как долгий процесс переживает падение процесса** — состояние шагов должно быть durable.
2. **Кто владеет последовательностью шагов** — доменный сервис, координатор или движок.
3. **Что происходит при отказе шага** — компенсация, повтор или остановка с ручным разбором.

Saga отвечает на (3) и частично на (1). Durable workflow отвечает на (1) и (2), а компенсации задаёт как паттерн внутри себя. Поэтому сравнение идёт по трём осям, а не «что лучше».

## 2. Варианты

| Вариант | Кто держит состояние | Где живёт логика |
|---|---|---|
| A. Хореографическая сага | доменные сервисы, каждый в своей БД | в подписках на события, распределена |
| B. Оркестрированная сага в домене | таблица состояний процесса в БД домена | конечный автомат в коде домена |
| C. Durable execution engine | движок (событийная история исполнения) | в коде workflow, который исполняет движок |

## 3. Сравнение по осям

### 3.1. Модель программирования и читаемость процесса

- **A.** Процесс не виден в одном месте: чтобы понять порядок, нужно сложить подписки нескольких сервисов. Изменение процесса затрагивает несколько сервисов. Зато связность между сервисами минимальна [Н].
- **B.** Процесс — явный автомат в одном месте; шаги и переходы читаются как код. Добавление шага — изменение одного сервиса.
- **C.** Процесс — обычная функция с `await` на вызовах активностей; движок делает её повторяемой после сбоя [В]. Самое читаемое представление процесса из трёх, но требует детерминизма кода workflow (см. 3.2).

### 3.2. Детерминизм и восстановление

- **C.** Требуется детерминированный реплей: при перезапуске воркер проигрывает историю и должен получить ту же последовательность событий [Н]. Нарушение детерминизма (случайность, время, порядок итерации по map, обращение к внешнему API из workflow) ломает восстановление. Это главная операционная ловушка движков: ошибки проявляются не при написании, а при первом реальном сбое.
- **B.** Восстановление — чтение состояния процесса из БД и продолжение с текущего шага. Детерминизма не требует: состояние материализовано, а не воспроизводится.
- **A.** Восстановление — у каждого сервиса своё; процесс в целом не имеет единой точки восстановления.

### 3.3. Ограничения на объём состояния

- **C (Temporal).** Жёсткий предел истории исполнения — 51 200 событий или 50 МБ на один workflow; сверх этого нужен Continue-As-New. Payload по умолчанию ограничен 2 МБ, крупные данные выносятся в blob-store по схеме claim-check [Н]. Длинная история замедляет реплей — явление называют «replay debt» [Н].
- **B.** Ограничение — только объём таблицы состояния и скорость её чтения; payload события ограничен шиной, а не движком.
- **A.** Ограничений нет по построению, но и гарантий нет.

Для платформы это существенно: команда K может нести до сотен килобайт (средний размер события на N2 — `L-EVENT-SIZE-N1N2`), и складывать её в историю движка с лимитом 2 МБ на payload допустимо, но на границе.

### 3.4. Операционная стоимость

- **C.** Отдельный компонент: сервер движка, его БД, воркеры, миграции схемы истории, мониторинг очередей задач [Н]. Исключение — DBOS: движок работает библиотекой внутри приложения и использует Postgres как слой долговечности, отдельного кластера нет [В].
- **B.** Дополнительных компонентов нет: таблица в существующей БД домена.
- **A.** Дополнительных компонентов нет, но диагностика распределена.

### 3.5. Лицензии (для D-8: self-hosted без вендора)

| Движок | Лицензия | Источник |
|---|---|---|
| Temporal (сервер) | MIT | [О] файл LICENSE в репозитории temporalio/temporal |
| Restate (сервер) | BSL (Business Source License); SDK — MIT | [В] заявление компании, файл LICENSE в restatedev/restate |
| DBOS Transact | MIT | [О] файл LICENSE в dbos-inc/dbos-transact-ts; MIT для остальных языков — по метаданным пакетов и заявлению вендора [В] |
| Hatchet, Inngest, Camunda | не проверялись по первоисточникам | [?] |

BSL для Restate означает «отложенный open source»: ограничения действуют сразу, открытая лицензия наступает через срок [Н]. Для self-hosted внутри организации это обычно допустимо, но требует чтения условий, а не ярлыка.

### 3.6. Работа при сетевых ограничениях и изоляции — ключевая ось для этой платформы

Это главное, что отличает наш случай от типового сравнения движков.

- **C.** Workflow исполняется воркером, который должен доходить до сервера движка; состояние шага фиксируется на сервере. Если узел изолирован от вертикали (N1 — `T_aut` минуты, приём K — до `D-K-REFUSAL`), воркер не может продвинуть workflow, потому что не может записать историю. Либо движок должен быть поднят на самом узле, либо долгий процесс на изолированном узле останавливается. У DBOS это ограничение мягче: историей служит Postgres, а Postgres на краю уже есть, и продвижение возможно локально [В].
- **B.** Состояние процесса — локальная таблица, поэтому процесс продолжается на изолированном узле так же, как обычная бизнес-операция. Компенсации, требующие соседей, ждут восстановления связи, но сам процесс не встаёт.
- **A.** Продолжение возможно по мере локально доступных событий; шаги, требующие недоступных сервисов, ждут.

Вывод по этой оси: для узлов N1–N2 durable engine допустим только в варианте «движок рядом с узлом» (DBOS-подобном), иначе он противоречит требованию автономной работы. Для N3 ограничение снимается.

### 3.7. Компенсации и идемпотентность

Все три варианта требуют идемпотентных компенсаций; различие — в том, кто гарантирует, что компенсация выполнится ровно один раз по эффекту.

- **C.** Движок повторяет активность до успеха, идемпотентность — на домене (`domain/0001`). Компенсация — такая же активность и получает те же гарантии.
- **B.** Повтор обеспечивает доменный обработчик шага; компенсация — отдельный шаг автомата, её идемпотентность тоже на домене.
- **A.** Компенсация — подписка на компенсирующее событие; гарантия повтора зависит от шины и от `domain/0001`.

Во всех вариантах вывод один: без `domain/0001` компенсации небезопасны, движок этого не исправляет.

## 4. Сводка

| Ось | A. Хореография | B. Оркестрация в домене | C. Durable engine |
|---|---|---|---|
| Читаемость процесса | низкая | высокая | высшая |
| Восстановление после сбоя | распределённое | из таблицы состояния | реплей истории |
| Детерминизм кода | не требуется | не требуется | **обязателен** |
| Предел истории | нет | объём таблицы | 51 200 событий / 50 МБ (Temporal) [Н] |
| Предел payload | шина | шина | 2 МБ по умолчанию (Temporal) [Н] |
| Доп. компоненты | нет | нет | сервер и БД движка, кроме DBOS |
| Лицензия | — | — | MIT / BSL (Restate) / MIT (DBOS) |
| Работа на изолированном узле | да | да | только при движке рядом с узлом |
| Компенсации | на домене | на домене | на домене |

## 5. Чем это заканчивается для X-4

Одно решение на все долгие процессы неверно: оси тянут в разные стороны. Предлагаемая форма для `domain/0009` — правило выбора, а не единый движок.

Кандидаты в требования (нумерация X-4.x для ADR):

1. **X-4.1. Процесс, у которого все шаги живут в одном узле и укладываются в `T_aut` класса узла, реализуется оркестрированной сагой в домене** (вариант B): таблица состояний, конечный автомат, компенсации как шаги. Движок не требуется, дополнительных компонентов нет.
2. **X-4.2. Durable execution engine допускается только там, где его состояние доступно исполнителю без вертикали** — то есть на N3 или в варианте движка, развёрнутого вместе с узлом (DBOS-подобного). Движок, требующий связи с центральным сервером на изолированном N1–N2, запрещён: он нарушает R-1 и R-14.
3. **X-4.3. Для движка обязателен явный лимит истории и payload**, проверяемый в конфигурации и в тестах: при превышении — Continue-As-New или вынос крупных данных в хранилище, а не рост истории.
4. **X-4.4. Компенсация каждого шага обязана быть идемпотентной по `domain/0001`**, независимо от выбранного варианта; наличие движка не считается заменой идемпотентности.
5. **X-4.5. Выбор варианта фиксируется в каталоге процесса** — у каждого долгого процесса указывается вариант (A/B/C), причина и владелец.
6. **X-4.6. Детерминизм кода workflow обязателен при варианте C** и проверяется тестом реплея на сохранённой истории; без такого теста движок не вводится в эксплуатацию.
7. **X-4.7. Хореография (A) допускается только для процессов с малым числом шагов и без явного владельца**, где распределение логики оправдано; для процессов с явным исходом и компенсациями она не применяется.

## 6. Что осталось не проверено

- Официальные условия BSL для Restate: срок и условия смены лицензии не читались, только заявление компании [В].
- Лицензии Hatchet, Inngest, Camunda/Zeebe по первоисточникам [?].
- Поведение движков при длительной изоляции узла (десятки часов) не описано ни одним источником для нашего сценария; вывод 3.6 — рассуждение из архитектуры движков, а не измерение.
- Число и длительность долгих процессов в реальной системе заказчиком не заданы; без этого нельзя выбрать, нужен ли движок вообще.
- Путь данных через хранилище payload (claim-check) не проверялся на совместимость с запретом потери K.
