# Вариант шины: NATS-центричный (вариант A) под гейтом fault-injection

## Context and Problem Statement

Платформе нужна шина, покрывающая иерархию узлов N0–N3, автономную работу при потере вертикали и федерацию регионов (требования R-1…R-4, D-1…D-6). Из раздела 6 требований известны три варианта: NATS-центричный, Kafka в ядре с лёгким краем, гибрид с P2P-слоем. Какой из них принять, зная, что независимый отчёт Jepsen по NATS 2.12.1 показал потерю подтверждённых записей?

## Decision Drivers

* Открытая лицензия и self-hosted без вендора (D-8).
* Иерархия leaf-узлов с outbound-only соединениями (D-1).
* Автономность узла при потере вертикали (R-1), горизонтальные связи (R-2).
* Запрет потери подтверждённых K (R-15) и результаты Jepsen по NATS 2.12.1.
* Экосистема аналитики и долгого хранения.

## Considered Options

* A. NATS-центричный: leaf nodes, JetStream domains, gateways.
* B. Kafka в ядре и регионах, лёгкий край (NATS или MQTT), мосты с пересчётом offsets.
* C. Гибрид с P2P-слоем (Zenoh) для горизонтальных связей и durable-журналом для K.

## Decision Outcome

Chosen option: «A. NATS-центричный», потому что одна технология покрывает иерархию, автономию и федерацию, а остальные варианты требуют второй технологии либо трансляции offsets с риском дублей.

Решение условное и остаётся `proposed`. Независимый отчёт Jepsen по NATS 2.12.1 показал потерю подтверждённых записей при повреждении файлов и при смене состава кластера, в том числе с `sync_interval: always`; утверждение ограничено версией 2.12.1. Перед фиксацией версии проводится собственный прогон сценариев R-13 на целевых объёмах, и фиксируется версия для установки. По состоянию на 2026-11-15 актуальна ветка 2.15.x; гейт должен указать конкретную версию, иначе он непроверяем.

Провал замера «сосед → сосед» сам по себе выбор не отменяет: этот механизм одинаково отсутствует во всех трёх вариантах (`0007`).

### Consequences

* Good, because одна технология покрывает иерархию, автономию и федерацию; лицензия Apache 2.0 (CNCF).
* Good, because leaf-узлы сами инициируют соединение, что соответствует D-1.
* Bad, because Jepsen по 2.12.1 зафиксировал потери подтверждённых записей даже с `sync_interval: always`; доверие к шине возможно только после собственного прогона.
* Bad, because семантика mirror/source между доменами JetStream не подтверждена независимыми источниками (условие 2 в `0009`).
* Bad, because экосистема аналитики и долгого хранения слабее, чем у Kafka.

### Confirmation

Условия `0009`: fault-injection (1), семантика mirror/source (2), замер задержки (3), пропускная способность каналов (4), soak на целевой нагрузке (5), замер «сосед → сосед» (6). До их выполнения статус остаётся `proposed`.

## Pros and Cons of the Options

### A. NATS-центричный

* Good, because закрывает иерархию, автономию и федерацию без второй технологии.
* Neutral, because пороги задержки и пропускной способности ещё не измерены.
* Bad, because корректность fsync требует собственного прогона после отчёта Jepsen.

### B. Kafka в ядре и регионах

* Good, because зрелость, экосистема, долгое хранение, tiered storage GA в 4.4.0.
* Neutral, because share groups с DLQ (KIP-1191) и tiered storage доставляются в 4.4.0.
* Bad, because тяжёл для автономного края и требует мостов с пересчётом offsets, что порождает дубли.
* Bad, because патч 4.3.2 закрывал два потенциальных data-loss в tiered storage — риск, требующий учёта при выборе этой ветки.

### C. Гибрид с P2P-слоем

* Good, because прямо отвечает на требование горизонтальных связей при редуцированных вертикальных (R-2).
* Neutral, because Zenoh даёт peer-обмен без второй инфраструктуры на узле.
* Bad, because добавляет вторую технологию и требует проверки долговечности; issue #2907 в Zenoh открыт.

## More Information

Если гейт не проходит, запасной путь — вариант B с ценой в виде мостов и риска дублей. Матрица сценариев и профили — `0009`. Смежные решения: `0002` (подтверждение), `0007` (горизонтальные связи).
