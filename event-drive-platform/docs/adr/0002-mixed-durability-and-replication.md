# Смешанный режим подтверждения: локальный fsync с зеркалом, асинхронная репликация

## Context and Problem Statement

Требование заказчика — не отклонять приём K из-за нехватки ёмкости и не терять принятое (R-14, R-15). Классическая схема кворумной записи (`RF ≥ 3`, `min.insync.replicas = 2`) на изолированном узле требует двух живых реплик, которых нет. Как обеспечить подтверждение K без потери и без отказа приёма на изолированном узле?

## Decision Drivers

* Инвариант K: подтверждённое событие не теряется (R-15).
* Запрет отказа приёма K при изоляции (R-14, решение заказчика до `D-K-REFUSAL`).
* Задержка подтверждения входит в p99 (P-2, P-5).
* Jepsen по NATS 2.12.1: потери подтверждённых записей есть и с `sync_interval: always` (раздел 4 требований, п. 1).

## Considered Options

* Кворумная запись `RF ≥ 3`, `min.insync.replicas = 2` на всех уровнях.
* Только локальный fsync без репликации.
* Смешанный режим: локальный fsync на зеркале плюс асинхронная репликация.
* Кворум только в ядре (N3), смешанный режим на N1–N2.

## Decision Outcome

Chosen option: «Кворум только в ядре (N3), смешанный режим на N1–N2», потому что на изолированном узле кворум недостижим, а в ядре изоляция маловероятна и кворум даёт дополнительную защиту.

Подтверждение K выдаётся после локальной durable-записи с зеркалом дисков (`D-MIRROR-COUNT`), репликация на два соседних узла класса идёт асинхронно и не блокирует приём. При работающей связи отставание репликации не превышает `D-LAG-LIMIT` (R-15).

### Consequences

* Good, because приём K не прекращается при потере связи с соседями — инвариант R-14 соблюдается.
* Good, because задержка подтверждения не зависит от доступности соседей.
* Bad, because полная потеря узла (пожар, отказ всех локальных дисков) в окне `D-LAG-LIMIT` теряет K, ещё не доехавшие до соседей. Заказчик принял этот риск.
* Bad, because требуется мониторинг состояния репликации по каждому K; без него окно риска невидимо.

### Confirmation

Сценарии fault-injection из `0009`: power loss и отказ диска после подтверждения не теряют подтверждённых K; при изоляции приём продолжается; lag по K не выше `D-LAG-LIMIT` (p100 за период теста).

## Pros and Cons of the Options

### Кворумная запись на всех уровнях

* Good, because подтверждённое событие гарантированно есть на нескольких узлах.
* Bad, because на изолированном узле двух живых реплик нет — приём K пришлось бы отклонять, что прямо запрещено заказчиком.

### Только локальный fsync

* Good, because максимально простой и быстрый путь подтверждения.
* Bad, because отказ узла без репликации теряет всё, что на нём было; при 48 ч окна это недопустимый объём.

### Смешанный режим

* Good, because совмещает запрет отказа с защитой от потери узла.
* Neutral, because требует явного учёта двух режимов в эксплуатации: N3 и N1–N2 ведут себя по-разному.
* Bad, because остаточный риск потери узла до репликации неустраним и должен быть принят явно.

## More Information

Требование R-15 — источник этого решения; ссылка на него добавлена в текст выше для трассировки. Условия проверки — `0009`. Параметры: `D-MIRROR-COUNT`, `D-LAG-LIMIT`, `D-REPLICA-COUNT`.
