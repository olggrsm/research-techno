# Удаление старых данных из истории без потери целостности

## Context and Problem Statement

История би-темпоральных таблиц и потоков событий растёт непрерывно. Удаление по одной строке ломает ссылочную целостность проекций и делает невозможным восстановление на момент до удаления. Как ограничить объём истории, сохранив восстанавливаемость?

## Decision Drivers

* Восстановление проекций должно работать после удаления (`domain/0004`).
* Аудит требует сохранять историю за заданный горизонт.
* Персональные данные подлежат удалению по требованию.

## Considered Options

* Удаление строк по одной старше срока.
* Партиционирование по времени и отсечение целых партиций со снимками.
* Бессрочное хранение всей истории.

## Decision Outcome

Chosen option: «Партиционирование по времени и отсечение целых партиций со снимками», потому что оно ограничивает объём атомарно и оставляет восстанавливаемый снимок на границе.

Таблицы истории и событий партиционируются по дате (день или месяц, в зависимости от потока); retention выражается как «держать N партиций», а удаление — `DROP PARTITION` старше границы. Снимок агрегата создаётся до отсечения, чтобы replay после границы начинался со снимка. Ссылки на удалённое заменяются на tombstone-записи, а не исчезают молча.

Границы retention задаются по классу данных: K-факты — не меньше горизонта аудита; персональные данные — по требованию их удаления, с обезличиванием в снимке.

### Consequences

* Good, because удаление атомарно и не оставляет «дыр» внутри периода.
* Good, because replay после границы возможен благодаря снимку.
* Bad, because горизонт удаления фиксируется заранее, и его изменение требует новой схемы партиционирования.
* Bad, because снимки сами занимают место и требуют своего retention.

### Confirmation

Тест: восстановление проекции исключительно из снимка и событий после границы даёт то же состояние, что полный replay. Проверка отсутствия молчаливых ссылок на удалённое — tombstone на месте удалённой записи.

## Pros and Cons of the Options

### Удаление строк

* Good, because гибко по срокам для каждой строки.
* Bad, because ломает целостность и делает восстановление невозможным; дорого по I/O.

### Партиционирование и отсечение

* Good, because атомарно, дёшево и восстанавливаемо.
* Neutral, because требует планирования схемы партиционирования.
* Bad, because фиксирует гранулярность удаления.

### Бессрочное хранение

* Good, because аудит полный всегда.
* Bad, because объём и стоимость растут без предела.
