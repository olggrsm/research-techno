# Порядок по объекту: партиционирование по шарду агрегата в выбранной шине

## Context and Problem Statement

Порядок нужен по объекту, а доступная гарантия — только в пределах ключа или партиции (P-7). Платформенный `0003` выбирает NATS-центричный вариант, где топиков и партиций Kafka нет: порядок задаётся subject и потоком JetStream. Как обеспечить порядок по объекту в этой шине, не опираясь на механизм, которого в архитектуре нет?

## Decision Drivers

* Порядок по объекту (`aggregate_id`) обязателен, между объектами — не обещается (P-7).
* Выбранная шина — NATS JetStream (`0003`); Kafka остаётся только запасным вариантом B.
* Расширение числа партиций меняет соответствие ключей партициям.
* K-команды и K-факты идут разными потоками (`0001`).

## Considered Options

* Ключ партиционирования `aggregate_id` в Kafka.
* Subject с сегментом шарда плюс JetStream-поток с ограниченным числом субъектов-фильтров.
* Единый subject на агрегат.

## Decision Outcome

Chosen option: «Subject с сегментом шарда плюс JetStream-поток», потому что оно даёт тот же эффект — один объект обрабатывается одним потребителем в порядке — в выбранной шине, без технологии, которой в архитектуре нет.

Схема subject: `k.cmd.<region>.<domain>.<verb>.<shard>.<object>` и `k.fact.<region>.<domain>.<object>.<event>`, где `shard = hash(aggregate_id) mod N`. Потребитель подписывается на свой набор шардов, и внутри шарда события обрабатываются последовательно. Число шардов фиксируется с запасом на горизонт роста и меняется только вместе с миграцией подписок, поскольку меняет соответствие объектов шардам.

Если гейт `0003` провалится и будет выбран вариант B, это решение переносится на Kafka без изменения принципа: ключ партиционирования — `aggregate_id`, число партиций фиксируется с запасом.

### Consequences

* Good, because порядок по объекту обеспечен в выбранной шине, а не в отсутствующей.
* Good, because один и тот же принцип применим к варианту B, если шина сменится.
* Bad, потому что: число шардов фиксируется заранее, и его изменение требует миграции подписок.
* Bad, потому что: горячий объект создаёт перекос: шард с ним обрабатывается медленнее остальных, и выравнивания танет.

### Confirmation

Тест разделения: события одного объекта, отправленные с двух сторон, применяются в порядке версий; при отказе потребителя шард продолжает обработку с последнего подтверждённого смещения. Проверка перекоса — метрика lag по шардам.

## Pros and Cons of the Options

### Ключ `aggregate_id` в Kafka

* Good, because привычно и хорошо документировано.
* Bad, because в выбранной архитектуре Kafka нет; решение описывало бы отсутствующий компонент.

### Subject с сегментом шарда

* Good, because работает в JetStream и сохраняет порядок по объекту.
* Neutral, because требует фиксированного числа шардов.
* Bad, потому что перекос по горячим объектам не выравнивается автоматически.

### Единый subject на агрегат

* Good, because максимальный порядок и простота.
* Bad, because число subjects растёт вместе с числом объектов — неуправляемо при миллионах объектов.

## More Information

Заменяет прежнюю версию решения о партиционировании Kafka, которая противоречила платформенному `0003`. При выборе варианта B — `kafka-partitioning-by-aggregate` как отдельная запись, а не как текущая.
