# Контракты событий: CloudEvents, schema registry, каталог и объявление модели согласованности

## Context and Problem Statement

K-факт публикуется всем подписчикам, и его схема эволюционирует независимо от потребителей. Требования задают формат (X-1), режим совместимости схем (X-2), каталог с владельцем типа (X-3), контрактные тесты (X-11) и обязательное объявление модели согласованности для каждого класса данных (R-11), но доменного решения, как это устроено, нет. Как объявлять и менять контракт события, не ломая подписчиков?

## Decision Drivers

* X-1: 100% событий в формате CloudEvents.
* X-2: schema registry с режимом не ниже BACKWARD.
* X-3: каталог AsyncAPI с владельцем каждого типа.
* R-11: каждый класс данных объявляет local-authoritative или eventually replicated.
* X-11: контрактные тесты блокируют несовместимый релиз.

## Considered Options

* Свободный JSON без реестра и каталога.
* CloudEvents плюс schema registry и каталог AsyncAPI с обязательными полями.
* Версионирование типа события в имени вместо реестра.

## Decision Outcome

Chosen option: «CloudEvents плюс schema registry и каталог AsyncAPI с обязательными полями», потому что только оно делает совместимость проверяемой в CI, а не декларативной.

Каждое событие публикуется в CloudEvents-оболочке с обязательными атрибутами, включая `id`, `source`, `type`, `time` и `datacontenttype`. Схема payload регистрируется в registry с режимом не ниже BACKWARD; CI блокирует несовместимое изменение (X-2). Каталог AsyncAPI содержит для каждого типа: владельца, поток (`k.cmd` / `k.fact` / `e`), модель согласованности и признак «ES или состояние».

Модель согласованности объявляется на уровне класса данных, а не типа события: `local-authoritative` означает, что владелец объекта — единственный источник истины и чтения идут к нему; `eventually replicated` означает, что допустимо чтение из проекции с отставанием. Значение обязательно, отсутствие — ошибка линтера каталога.

### Consequences

* Good, because несовместимое изменение схемы ловится в CI, а не в продакшене.
* Good, because R-11 становится проверяемым требованием, а не пожеланием.
* Bad, because каталог нужно поддерживать, и он становится частью процесса релиза.
* Bad, because BACKWARD ограничивает некоторые изменения удобных структур.

### Confirmation

CI-проверки: каталог валиден по схеме AsyncAPI; у каждого типа есть владелец, поток и модель согласованности; изменение схемы проходит проверку совместимости; контрактные тесты потребителей (`can-i-deploy`) зелёные.

## Pros and Cons of the Options

### Свободный JSON

* Good, because не требует инфраструктуры.
* Bad, because совместимость не проверяема, а X-1…X-3 не выполняются.

### CloudEvents, registry и каталог

* Good, because делает контракт проверяемым и связывает R-11 с каталогом.
* Neutral, because требует дисциплины при релизе.
* Bad, because ограничивает свободу изменения схем.

### Версия в имени типа

* Good, because просто и видно глазами.
* Bad, because дублирует реестр и не даёт автоматической проверки совместимости.
