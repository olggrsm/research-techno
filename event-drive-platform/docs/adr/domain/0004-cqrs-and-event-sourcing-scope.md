# CQRS и Event Sourcing: где применяем, а где нет

## Context and Problem Statement

Event Sourcing даёт полный аудит и восстановление состояния из событий, но требует event store, проекций и постоянного процесса восстановления. CQRS разделяет запись и чтение, что вводит отставание проекций. Где эти подходы оправданы, а где достаточно обычного состояния?

## Decision Drivers

* R-11: каждый класс данных обязан объявить модель согласованности.
* Аудит и replay нужны не всем сервисам одинаково.
* Стоимость эксплуатации проекций и восстановления — постоянная.

## Considered Options

* Event Sourcing по умолчанию для всех сервисов.
* Event Sourcing выборочно: финансы, резервирования, длинные истории статусов.
* Только состояние в БД без ES и CQRS.

## Decision Outcome

Chosen option: «Event Sourcing выборочно», потому что история растёт без ограничений и восстановление проекций становится обязательным процессом, а выгода есть только там, где аудит и replay действительно нужны.

Event Sourcing применяется там, где нужен полный аудит и восстановление состояния из событий: финансовые операции, резервирования, изменения статусов с длинной историей. В остальных местах — обычное состояние в БД с публикацией факта через transactional outbox (`domain/0007`); шина не обязана быть источником истины.

Где ES применяется, поток событий агрегата — источник истины, проекции строятся отдельно и отстают, что даёт eventual согласованность чтения. Команды идут на запись, запросы — в проекции; это разделение и есть CQRS.

### Consequences

* Good, because стоимость ES и проекций платится только там, где они оправданы.
* Good, because большинство сервисов остаётся простыми: состояние в БД плюс outbox.
* Bad, because в одном домене сосуществуют две модели, и граница между ними должна быть объявлена явно.
* Bad, because для сервисов с ES восстановление проекций — обязательный операционный процесс.

## Pros and Cons of the Options

### ES по умолчанию

* Good, because единообразие и полный аудит везде.
* Bad, because история растёт без границ, восстановление проекций обязательно для всех.

### ES выборочно

* Good, because стоимость соразмерна потребности.
* Neutral, because требует явной границы между классами данных.
* Bad, because две модели сосуществуют в одном домене.

### Только состояние

* Good, because самый простой путь.
* Bad, because аудит и восстановление на момент времени недоступны без отдельных усилий.
