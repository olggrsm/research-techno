# Транзакционная граница: outbox между БД сервиса и публикацией события

## Context and Problem Statement

P-8 требует transactional outbox/inbox. Доменное изменение и публикация события — две разные системы, и сбой между ними даёт либо изменение без события, либо событие без изменения. Где проходит граница транзакции и кто отвечает за публикацию?

## Decision Drivers

* P-8: связь БД и событий — через transactional outbox/inbox; 0 потерянных и 0 повторных эффектов.
* R-15: подтверждённое K не теряется.
* `domain/0004`: ES применяется выборочно, в остальных случаях — состояние плюс outbox.
* Шина не обязана быть источником истины.

## Considered Options

* Публикация из бизнес-кода после коммита.
* Outbox-таблица в транзакции с изменением и отдельный публикатор.
* Двухфазный коммит между БД и шиной.

## Decision Outcome

Chosen option: «Outbox-таблица в транзакции с изменением и отдельный публикатор», потому что публикация из бизнес-кода не атомарна, а двухфазный коммит между БД и внешней шиной не поддерживается.

Изменение состояния и запись в `outbox` идут одной транзакцией БД. Отдельный публикатор читает `outbox` в порядке вставки, публикует в шину и отмечает запись как отправленную. Повторная публикация допустима: потребитель дедуплицирует (`domain/0001`). Гарантия — at-least-once плюс идемпотентность, exactly-once только как эффект.

Для K-команд outbox — единственное место, откуда событие попадает в шину; приложение не публикует напрямую. Входящие события обрабатываются через inbox-таблицу: запись `event_id` и бизнес-изменение одной транзакцией.

### Consequences

* Good, because сбой между изменением и публикацией не теряет событие и не создаёт изменение без события.
* Good, because повтор публикации безопасен при идемпотентном потребителе.
* Bad, because появляется задержка публикации: событие уходит после коммита, а не в момент изменения.
* Bad, because публикатор — отдельный компонент, который нужно эксплуатировать и мониторить (lag outbox).

### Confirmation

Fault-injection: падение процесса между записью в БД и публикацией — после перезапуска событие публикуется ровно один раз с точки зрения потребителя. Метрика: возраст старейшей непубликованной записи в `outbox`.

## Pros and Cons of the Options

### Публикация из бизнес-кода

* Good, because просто и без дополнительного компонента.
* Bad, because не атомарна: сбой между коммитом и публикацией теряет событие.

### Outbox и публикатор

* Good, because атомарность через транзакцию БД, потери исключены.
* Neutral, because требует таблицы и фонового процесса.
* Bad, because добавляет задержку и точку мониторинга.

### Двухфазный коммит

* Good, because строгая атомарность в теории.
* Bad, because не поддерживается между БД и шиной; на практике недостижим.
