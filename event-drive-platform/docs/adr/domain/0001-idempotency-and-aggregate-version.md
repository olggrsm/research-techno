# Идемпотентность и версия агрегата

Доставка at-least-once, поэтому повтор — норма, а не исключение. Повторяющаяся операция не должна менять состояние, а позднее событие не должно перетирать более новое.

Решение двухслойное. Первый слой — версия агрегата: событие применяется только если `event_version` строго больше текущей, проверка идёт условным `UPDATE … WHERE version < :event_version` в той же транзакции, что и бизнес-изменение. Второй слой — идемпотентность самой операции: `INSERT … ON CONFLICT DO NOTHING` по внешнему ключу, ledger для денег и остатков (баланс — производная от неизменяемых записей), сохранение `IN_PROGRESS` с `idempotency_key` перед внешним вызовом и запрос статуса по ключу вместо слепого повтора.

Обоснование отказа от таблицы `processed_events` как основного механизма: при потоке N3 (110 000 событий/с) и TTL 7 суток она даёт 6,65 × 10¹⁰ строк на одного потребителя — около 8 ТБ без индекса и 13 ТБ с ним, при вставках, вдвое-втрое превышающих возможности одной СУБД. Таблица остаётся только для неидемпотентных внешних вызовов, где объём определяется их числом.

**TTL:** 7 суток для K (перекрывает 48 ч valid-until, retention и replay из DLQ), 3 суток для E.
