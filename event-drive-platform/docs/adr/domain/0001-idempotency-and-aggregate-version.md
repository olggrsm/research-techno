# Идемпотентность и версия агрегата

## Context and Problem Statement

Доставка at-least-once, поэтому повтор — норма, а не исключение. Как сделать так, чтобы повторяющаяся операция не меняла состояние, а позднее событие не перетирало более новое?

## Decision Drivers

* P-8: потребители обязаны быть идемпотентны, связь БД и событий — через outbox/inbox.
* R-16: K-команда должна давать exactly-once эффект.
* Поток N3 (`L-N3-K-RATE-FULL`) исключает таблицу дедупликации по всем событиям.

## Considered Options

* Таблица `processed_events` как основной механизм для всех событий.
* Версия агрегата плюс идемпотентность самой операции.
* Только брокерная exactly-once семантика (транзакции продюсера).

## Decision Outcome

Chosen option: «Версия агрегата плюс идемпотентность самой операции», потому что таблица по всем событиям не масштабируется, а брокерная семантика не распространяется на БД и внешние системы.

Первый слой — версия агрегата: событие применяется только если `event_version` строго больше текущей, проверка идёт условным `UPDATE … WHERE version < :event_version` в той же транзакции, что и бизнес-изменение. Второй слой — идемпотентность операции: `INSERT … ON CONFLICT DO NOTHING` по внешнему ключу, ledger для денег и остатков (баланс — производная от неизменяемых записей), сохранение `IN_PROGRESS` с `idempotency_key` перед внешним вызовом и запрос статуса по ключу вместо слепого повтора.

Таблица `processed_events` остаётся только для неидемпотентных внешних вызовов: при потоке N3 и TTL 7 суток она дала бы десятки миллиардов строк на потребителя при вставках, кратно превышающих возможности одной СУБД.

### Consequences

* Good, because механизм масштабируется вместе с потоком: объём зависит от числа внешних вызовов, а не от числа событий.
* Good, because conditional update закрывает и дубли, и события вне порядка одним условием.
* Bad, because при конфликте версии нужно перечитать агрегат и повторить решение; логика повтора должна быть ограничена.
* Bad, because для событий без версии (внешние источники) нужен отдельный путь — `occurred_at` или монотонный sequence.

### Confirmation

Тесты: повторная доставка не меняет состояние; параллельная доставка двух копий создаёт один побочный эффект; сбой после бизнес-операции до ack не дублирует операцию; устаревшее событие не перезаписывает новое. TTL дедупликации — `domain/0008`.

## Pros and Cons of the Options

### `processed_events` для всех событий

* Good, because простой и прямолинейный механизм.
* Bad, because при целевом потоке объём и число вставок превышают возможности одной СУБД.

### Версия агрегата плюс идемпотентность операции

* Good, because масштабируется, закрывает порядок и дубли вместе.
* Neutral, because требует дисциплины: каждая операция проектируется идемпотентной.
* Bad, because конфликты версии требуют перечитывания и повтора решения.

### Только брокерная exactly-once

* Good, because не требует изменений в домене.
* Bad, because не распространяется на БД и внешние системы — граница гарантии проходит по брокеру.
