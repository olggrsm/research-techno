# Разделение критичных событий на K-команды и K-факты

## Context and Problem Statement

Шина несёт два непохожих потока критичных событий, и в постановке заказчика оба названы категорией K. Команда требует адресации владельцу и срока актуальности, факт — публикации всем подписчикам и упорядочивания по объекту. Если держать их в одной категории, приходится выбирать один режим SLO, повторов и маршрутизации на оба потока. Как разделить K, чтобы и адресация, и порядок, и повторы были заданы для каждого потока отдельно?

Термины — `GLOSSARY.md`: K-команда, K-факт, владелец объекта, valid-until.

## Decision Drivers

* Запрет потери K для обоих потоков (раздел 3 требований).
* Команда адресуется владельцу объекта и не может быть broadcast-подпиской (R-17).
* Команда исполняется с exactly-once эффектом (R-16); факт требует порядка по объекту.
* Скорости и объёмы потоков различаются на порядок (`L-CMD-FACT-RATIO`).

## Considered Options

* Единая категория K с одним набором правил.
* Разделение на K-команду и K-факт с раздельными пространствами имён.
* Только факты, команды вне шины (чистая хореография по клиппингу `eda-principals.md`).

## Decision Outcome

Chosen option: «Разделение на K-команду и K-факт с раздельными пространствами имён», потому что только оно даёт каждой семантике собственный режим, не ослабляя запрет потери.

K-команда — событие, адресованное владельцу объекта, с valid-until `D-K-RETENTION` и exactly-once эффектом. K-факт — доменное событие, публикуемое владельцем всем подписчикам, упорядочиваемое версией агрегата; срок актуальности к нему не применяется. Потоки разделены физически: `k.cmd.>` и `k.fact.>` с разными ACL, продюсерами и группами потребителей (D-2); скорости делятся пропорцией `L-CMD-FACT-RATIO`.

### Consequences

* Good, because команды получают маршрутизацию и срок актуальности, а факты — broadcast и порядок по объекту, без компромисса между ними.
* Good, because SLO, партиционирование и дедупликация задаются независимо для каждого потока.
* Bad, because два набора SLO, два способа партиционирования и две группы потребителей вместо одной.
* Bad, because дедупликация и идемпотентность команд уходят в доменный слой и не могут быть гарантированы шиной.

### Confirmation

Проверяется ревью конфигурации: ни один аккаунт не имеет wildcard-доступа, покрывающего оба префикса; в каталоге событий у каждого типа указан поток. Соотношение скоростей — `tools/check-params.py` по `L-CMD-FACT-RATIO`.

## Pros and Cons of the Options

### Единая категория K

* Good, because проще эксплуатация: один набор политик и одна группа потребителей.
* Bad, because команда и факт требуют разных гарантий по адресации, сроку и повторам; единый режим либо избыточен для факта, либо недостаточен для команды.

### Разделение на K-команду и K-факт

* Good, because каждая семантика получает собственный режим.
* Neutral, because требует дисциплины в именовании пространств имён.
* Bad, because добавляет сущности в модель и в каталог событий.

### Только факты

* Good, because соответствует правилу «публикуйте факт, а не команду» и снимает необходимость в адресации.
* Bad, because заказчик назвал команды запуска процессов критичными, и их отказ от доставки адресату пришлось бы компенсировать в домене без гарантий шины.

## More Information

Смежный ADR: `domain/0003` (порядок по агрегату). Параметры: `L-CMD-FACT-RATIO`, `D-K-RETENTION`.
