# Девять напряжений требований, под которые раскладываются решения

## Context and Problem Statement

Требования задают конфликты, которые нельзя снять одновременно: каждое решение выбирает, в какую сторону снимается хотя бы одно из них. Где фиксировать эти напряжения, чтобы новое решение проверялось против них, а не открывало их заново?

## Decision Drivers

* Решения каталога должны иметь объяснение, почему они приняты именно так.
* Устаревший документ `docs/ADR-001-architecture-approach.md` больше не источник истины.
* Верификация ADR должна проверять решения против списка напряжений.

## Considered Options

* Хранить напряжения только в устаревшем общем документе.
* Завести отдельный ADR со списком напряжений и ссылками на решения.
* Разнести напряжения по соответствующим решениям без общего списка.

## Decision Outcome

Chosen option: «Отдельный ADR со списком напряжений», потому что он даёт одно место для проверки и не размывает отдельные решения.

### Напряжения и решения, которые их снимают

1. **Долговечность и задержка** (P-3, P-5, R-3) — fsync перед подтверждением повышает p99, но без него подтверждённые записи теряются при коррелированных отказах. Jepsen по NATS 2.12.1: 679 153 потерянных из 1 367 069 в одном прогоне, причём потери есть и с `sync_interval: always`. Снимается `0002`.
2. **Автономность и безопасность** (R-1, R-9, R-10) — долгоживущие сертификаты покрывают изоляцию, но откладывают отзыв прав. Снимается `0005`.
3. **Автономность и согласованность** (R-11) — при разделении доступны только eventual и causal модели. Остаётся открытым по своей природе: каждый класс данных обязан объявить модель согласованности. Механизм объявления — доменный ADR `domain/0006`.
4. **Порядок и масштаб** (P-7) — строгий порядок в пределах ключа ограничивает параллелизм потребления. Снимается `0001` и доменным `domain/0003`.
5. **Exactly-once и границы системы** (P-8) — гарантия брокера не распространяется на БД и внешние системы. Снимается `0001` и доменными `domain/0001`, `domain/0007`.
6. **Ёмкость и длительность изоляции** (R-6, R-7, R-14) — отказ приёма K допустим только после `D-K-REFUSAL`, а резерв считается на `D-K-RETENTION`. Снимается `0004`.
7. **P2P-обмен и долговечный журнал** (R-2, R-3) — peer-to-peer даёт горизонтальные связи, но не гарантирует долговечность. Снимается `0007`: механизм не выбран, Zenoh не берётся в основу.
8. **Команды K и актуальность** (R-17, R-18) — команда с valid-until `D-K-RETENTION` может устареть при долгой изоляции, и исполнение по устаревшему решению опаснее потери. Снимается `0001`: «не терять» означает «исход всегда зафиксирован».
9. **Команды K на обеих сторонах разделения** (R-17) — приём команд по обе стороны разрыва расходится после реконвергенции. Снимается `0001` и `domain/0003`: single-writer по объекту, цена — недоступность модификации, пока недоступен владелец.

### Consequences

* Good, because решения проверяются против списка напряжений, а не изобретаются заново.
* Good, because исчезла зависимость от легаси-записей `memory/decisions/`, которые не поддерживаются.
* Bad, because список нужно поддерживать при появлении новых требований.

### Confirmation

Ревью нового ADR проверяет, какое напряжение он снимает и не нарушает ли уже снятое.

## Pros and Cons of the Options

### Только устаревший общий документ

* Bad, because при расхождениях каталог оставался бы без объяснения, почему решения приняты именно так.

### Отдельный ADR со списком

* Good, because одно место для проверки и ссылок.
* Neutral, because требует актуализации при изменениях каталога.

### Разнести по решениям

* Good, because напряжение видно рядом с решением.
* Bad, because теряется общий взгляд и дублируются формулировки.
