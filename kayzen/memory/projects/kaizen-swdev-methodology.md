# Kaizen-методология для разработки ПО — план исследования

Источник ТЗ: `DESCRIPTION.md` (в корне репозитория). Итоговая методология состоит из трёх документов
(Видение → Описание методологии → План внедрения); этот план покрывает **только
документ 1 — «Видение»**. Планы для документов 2 и 3 будут оформлены отдельно,
после того как «Видение» пройдёт review.

Источники: (a) уже накопленная база фактов кайдзен в `memory/facts/` (см.
[[memory/_views/by-predicate]]), (b) внешний веб-поиск по современным проблемам
разработки ПО и практикам компаний.

## Этап 0 — База знаний по кайдзен (готово)

Уже покрыто фактами в `memory/facts/`: `kaizen`, `gemba`, `5s`, `pdca`, `sdca`,
`muda`/`mura`/`muri`, `lean-production`, `toyota-production-system`,
`lean-six-sigma`, роли Imai/Ohno/Ishikawa/Kume. Источник — 7 статей в
`Clippings/`. Достаточно для раздела «сравнительный анализ» документа Видение;
дополнительной обработки не требуется, если не найдутся новые статьи.

## Этап 1 — Ключевые проблемы разработки ПО (2026) [готово]

Вопрос: какие проблемы разработки и управления изменениями требований в
жизненном цикле продукта сейчас (2026) считаются ключевыми — с чем реально
борются команды.

Кандидаты направлений поиска:
- стоимость и предсказуемость изменения требований на позднем этапе (cost of
  change curve, критика Waterfall vs Agile)
- технический долг и деградация архитектуры при частых изменениях
- разрыв между бизнес-требованиями и реализацией (несостыковка ожиданий)
- масштабирование Agile/Scrum в крупных организациях (SAFe-критика,
  "agile fatigue")
- влияние AI-ассистированной разработки на качество и скорость (2025-2026)
- измерение качества и производительности команд (DORA-метрики, критика
  code-freeze практик)

Метод: WebSearch/WebFetch по каждому направлению, 2024-2026 источники
(отраслевые отчёты, инженерные блоги, State of Agile / DORA / Stack Overflow
survey и т.п.).

Результат: `insight`-записи в `memory/insights/` (schema: type, title,
recorded_at, summary, entities, sources, confidence), одна на направление —
затем синтез в раздел «ключевые проблемы» документа Видение.

## Этап 2 — Тенденции и перспективные подходы [готово]

Вопрос: какие подходы сейчас позиционируются как решение проблем из Этапа 1.

Кандидаты: эволюционная архитектура (Ford/Parsons/Kua), Platform Engineering,
Team Topologies, Continuous Discovery/Delivery, DevOps/SRE практики,
трихотомия build-measure-learn, AI pair-programming и agentic coding как
ускоритель цикла PDCA.

Метод: веб-поиск + сопоставление с уже известными кайдзен-циклами PDCA/SDCA
(см. `memory/facts/pdca/`, `memory/facts/sdca/`) — фиксировать, где подход уже
пересекается с кайдзен-практиками, а где расходится.

Результат: `insight`-записи, плюс при необходимости новые факты
`related-concept`/`component-of` для существующих кайдзен-сущностей (через
`tools/transact.py`, как в предыдущих транзакциях).

## Этап 3 — Компании и команды с эффективными практиками [готово]
Вопрос: кто на практике реализует данные подходы наиболее результативно —
конкретные компании/команды, что именно они делают, есть ли подтверждённые
результаты (метрики, кейсы).

Кандидаты для проверки (не итоговый список): Spotify (Team Topologies),
Amazon (two-pizza teams, working backwards), Netflix (chaos engineering,
freedom & responsibility), Google (SRE, DORA), а также любые компании,
явно ссылающиеся на кайдзен/lean в разработке ПО.

Метод: веб-поиск по каждой компании, приоритет — первичные источники
(инженерные блоги, конференционные доклады) над вторичными пересказами.

Результат: `insight`-записи с `entities` на соответствующие org-сущности
(зарегистрировать новые сущности в `memory/entities.md` при необходимости).

## Этап 4 — Сравнительный анализ и выводы [готово, ожидает review]

Вопрос: как современные подходы (Этапы 1-3) соотносятся с кайдзен-подходом
(Этап 0) — что совпадает, что противоречит, в чём кайдзен даёт
дополнительную ценность для разработки ПО в парадигме эволюционной
архитектуры.

Метод: синтез без новых источников — только опираясь на insight-записи
Этапов 0-3. Кандидатный формальный шаг: зафиксировать итоговые тезисы как
`decision`-записи (`memory/decisions/`, id `DEC-0xx`) там, где нужен явный
review перед тем, как тезис попадёт в документ Видение.

Результат: два синтезирующих insight-файла —
[[memory/insights/comparative-alignment-2026]] (где современные подходы
структурно совпадают с PDCA/SDCA/gemba без кайдзен-терминологии) и
[[memory/insights/comparative-tension-2026]] (где расходятся: SAFe
сверху-вниз vs gemba-инициатива, устойчивый темп vs "unforgiving culture"
Netflix, расхождения в достоверности заявлений об ускорении). Три
итоговых тезиса зафиксированы как `decision`-записи со статусом
`proposed`, ожидающие явного review перед включением в документ
«Видение»: [[memory/decisions/DEC-001]] (инициатива улучшения — с gemba,
не сверху), [[memory/decisions/DEC-002]] (устойчивый темп/не-muri —
обязательный критерий оценки практики, не только результат),
[[memory/decisions/DEC-003]] (ценность документа — единый словарь для
уже распространённых практик, а не новизна самого кайдзен).

## Этап 5 — Черновик документа «Видение»

Собрать разделы по структуре ТЗ (≤10 страниц): ключевые проблемы → тенденции
и подходы → практики компаний → выводы сравнительного анализа. Черновик —
отдельный markdown-документ вне `memory/` (например `docs/vision.md`), не
подчиняется v4-протоколу памяти напрямую, но каждое фактическое утверждение
в нём должно трассироваться на `insight`/`fact`/`decision`-запись в `memory/`.

## Критерии готовности этапа (Видение)

- Каждое утверждение о проблеме/тренде/компании имеет `insight`- или
  `fact`-запись с `sources`.
- `tools/lint.py` проходит без ошибок после каждой транзакции.
- Документ ≤10 страниц, содержит все 4 требуемых раздела.
- Раздел выводов явно ссылается на конкретные кайдзен-концепции
  (`kaizen`, `gemba`, `pdca`/`sdca`, `muda`/`mura`/`muri`) через wikilink на
  `memory/facts/`.

## Открытые вопросы / риски

- Компании из Этапа 3 могут не иметь публичных первичных источников —
  тогда снижать `confidence` до `medium`/`low` и явно это отмечать.
- Веб-поиск может дать противоречивые оценки одного и того же подхода —
  фиксировать оба insight и явно отмечать противоречие, не сглаживать.
